        系统功能文档
        
          
        详细说明各模块的职责、数据流、触发逻辑、过滤规则与排错建议。
        
        
        
        
        
          
        1. trigger_process_queue 是什么
        
          
        
            trigger_process_queue 是“立即处理 follower_queue”的手动触发任务。
            触发后执行 tiktok_follow_scraper.py --mode process_queue。
            其目的：把 follower_queue 中待处理 follower 的 following 关系转化为新的 root 候选，并回流到业务队列。
            单次处理条数由页面「直客访问模式数据」中的 process_queue_batch_size 输入框作为查询参数 limit 传给 /api/admin/tasks/trigger_process_queue（与设备 /api/pull_username 的 pull_batch_size 无关）。
          
        
          
          
            
        • 业务队列：mobile_pending_usernames（增长模式下发池）。
          • 
            
        • root 候选：tiktok_roots（新发现根用户池）。
          • 
          
        

          
        2. 随机抽取一批（来自 tiktok_roots）的标准流程（严格版）
        
          
          
            
        1. 读取批次：从 follower_queue 按创建时间读取待处理记录（支持 limit）。
          2. 
            
        2. 进入主页：优先直接访问 https://www.tiktok.com/@用户名，失败再走搜索页兜底。
          3. 
            
        3. 主页可用性判断：若主页打不开，标记 following_access_status=not_found，并标记 mobile_push_status=not_eligible。
          4. 
            
        4. 粉丝账号私密拦截：若 follower 主页是私密账号，标记 following_access_status=private_account，并标记 mobile_push_status=not_eligible。
          5. 
            
        5. 采集 following：打开关注列表，滚动采集前 N 个用户名。
          6. 
            
        6. following 列表不可见判定：命中“关注列表私密/隐藏”文案或空列表容器（多语言关键词），视为不可见；该 follower 标记 following_access_status=following_private，mobile_push_status=not_eligible。
          7. 
            
        7. 入库前单次评估（一次查询）：每个 following 仅调用一次 autoSearch，完成：
              
            
                
          • 私密判断：private_account_guess=true 直接拦截；
            • 
                
          • 质量阈值：video_count > following_filter_min_video_count 且 following_count < following_filter_max_following_count；
            • 
                
          • 字段不全/查询失败也拦截（fail-closed）。
            • 
              
          
            
          8. 
            
        8. 落库：仅对通过评估且原本不在 tiktok_roots 的 following，写入 tiktok_roots + mobile_pending_usernames。
          9. 
            
        9. 状态回写与清理：
              
            
                
          • 有 following 入库尝试时：follower 标记 following_access_status=available，mobile_push_status=pending；
            • 
                
          • 本轮处理过的 follower 最终会从 follower_queue 删除。
            • 
              
          
            
          10. 
          
        

          
        3. 落库前过滤规则（来源于 tiktok_roots / follower_queue 两条链路）
        
          
          
            
        1. tiktok_roots -> follower_queue（collect_roots）
              
            
                
          • root 入库前先做私密判定；判定失败或私密则不写 tiktok_roots。
            • 
                
          • 每个 follower 入队前再做一次私密判定；私密/判定失败直接拦截，不写 follower_queue。
            • 
              
          
            
          2. 
            
        2. follower_queue -> following 回流（process_queue）
              
            
                
          • following 先过私密判定，再过质量阈值判定；
            • 
                
          • 仅通过者写入 tiktok_roots 与 mobile_pending_usernames；
            • 
                
          • 已存在于 tiktok_roots 的 following 不重复写入下发池。
            • 
              
          
            
          3. 
          
        

          
        4. 设备端三种模式：详细步骤、页面流转与判定逻辑
        
          
        
            关于无障碍：主流程以 root input tap / screencap + OCR 为主。无障碍未连接时任务仍可执行（使用 Application 上下文取分辨率与缓存目录）。无障碍服务仅在少数能力上有用（例如可选的贝塞尔滑动 dispatchGesture、未连接时 scrollFeed 会回退为 root input swipe）。建议仍可在系统设置中开启，以便将来扩展依赖无障碍节点的步骤。
          
        

          
        4.1 growth 模式（涨粉模式）
        
          
          
            
        1. 设备端调用 /api/pull_username 拉取用户名；服务端数据源为 mobile_pending_usernames。
          2. 
            
        2. 首次打开 TikTok（非复用 Users 路径）：delay(500) 后执行 runForYouWarmupIfNeeded（见 4.7），再点击放大镜进入搜索。
          3. 
            
        3. 页面流转（客户端）：搜索结果页 -> Users 列表 -> 目标用户主页 -> Followers 列表。
          4. 
            
        4. 进入 Users 列表（含完整验收）：先执行 OCR Fast 查找 “Users” 标签并点击；若首次未命中或点击后页面无变化，再执行 OCR Fallback 二次识别。验收标准：顶部标签区出现 Users 激活态，且列表中可见多个用户结果（如昵称/Follow 文案）；未通过则回到搜索结果页重新触发一次。
          5. 
            
        5. 进入目标主页（避免误点）：在 Users 列表对 OCR 文本做统一归一化（去空格/大小写/符号）后，与目标 username 做相似度匹配，按“最高分且超过阈值”选择唯一候选并点击。验收标准：主页出现目标用户名（或高置信度变体）且头像/作品区加载完成；若进入他人主页或未加载成功，则返回 Users 列表重试，超过重试上限记失败并换下一个任务。
          6. 
            
        6. 进入 Followers 列表（点击 + 校验闭环）：当前实现为固定比例坐标点击（见下文「4.4 固定坐标表」Followers 行）+ 帧差校验；点击后通过 帧差阈值 判断是否进入列表页。若未进入则重试；连续失败则结束该用户名流程并上报失败原因。
          7. 
            
        7. 进入作品页判定策略（growth）：在粉丝主页随机点击左/中/右作品位（日志带 post_slot=left|middle|right）。若命中左列，直接视为进入成功并开始互动；若命中中/右列，则使用“点击前基准帧 vs 点击后帧”的前后帧差判定（点击后等待 growth_post_check_after_tap_delay_ms，默认 1000ms），失败后再按 growth_post_second_check_delay_ms（默认 650ms）进行二次判定；中/右列路径下帧差判定不启用评论框 OCR 兜底（与早期文档表述不一致者以代码为准）。
          8. 
            
        8. 进入作品页后的等待：video_stay_min / video_stay_max 随机停留（秒）在 **growth** 与 **live/direct** 下均生效——growth 在粉丝作品互动开始前等待；live/direct 在首条作品判定通过后、互动开始前等待。
          9. 
            
        9. 涨粉模式评论：不再使用 OCR 定位「Add comment...」点开评论框，改为固定比例点击 (0.92 × 屏宽, 0.68 × 屏高)；输入文案后发送按钮策略与 live 文本评论一致（见下文「评论发送」）。
          10. 
            
        10. 下发与去重：mobile_pending_usernames 仅 pending 可被拉取；拉取后变 sent；设备上报**成功**时删除对应队列行，失败则标记 failed 保留。历史数据不会在正常运行中批量清除（除一次性 DB 迁移或运维脚本外）。
          11. 
            
        11. 设备随后在 Followers 列表内按 processFollowersList 执行访问/互动：外层最多 8 轮（rounds < 8），每轮 OCR 取行、逐条处理后可下滑；到底则提前结束。单条粉丝上若配置 skip_post_click_prob 且随机命中，则不再进入点作品流程（先尝试与无作品/私密相同的 OCR 回退；否则强制 back 离开主页）。帧差类日志带 username 与 post_slot 便于绑定主任务用户与所点作品列。
          12. 
          
        

          
        4.2 live 模式（主播访问模式）
        
          
          
            
        1. 设备端调用同一拉取接口；服务端数据源：live_customer；按批大小返回并可累计使用计数。
          2. 
            
        2. 页面流转（客户端）：搜索结果页 -> Users 列表 -> 目标用户主页 -> 首条作品详情页。
          3. 
            
        3. 进入 Users 后增加验收：通过 OCR 统计 Follow 文案数量，目标阈值 >= 3；不足时补点 Users 并重验。
          4. 
            
        4. 进入作品页：固定点击左侧第一条作品，采用“两次判定”策略；判定方式为 帧差 + 评论输入区 OCR。
          5. 
            
        5. 互动阶段：执行评论/点赞/收藏/转发（受日限控制），完成后返回到 Users 选择界面并清空搜索框。
          6. 
          
        

          
        4.3 direct 模式（直客访问模式，run_mode=direct）
        
          
          
            
        1. 设备端调用拉取接口；服务端数据源：follower_queue。
          2. 
            
        2. 页面流转（客户端）：搜索结果页 -> Users 列表 -> 目标用户主页 -> 首条作品详情页。
          3. 
            
        3. 进入作品页：固定点击左侧第一条作品（坐标比例同 live，见「4.4」）；不做 Search/评论区 OCR 判定，点击成功与否仅依赖 root tap 返回值。
          4. 
            
        4. 互动触发时机：点击首条作品后等待 direct_post_action_delay_ms（默认 1500ms，范围 300~8000ms）后直接开始互动。
          5. 
            
        5. 互动阶段：严格遵循后台互动配置（权重、action_single、每日上限、互动间隔范围），不再默认全部执行。direct 下收藏、转发、评论框入口均为固定坐标点击。
          6. 
            
        6. 后续可由后台执行 trigger_process_queue，将队列关系扩展后回流到 tiktok_roots 与下发池。
          7.

        4.7 延时与「用户资料主页」停留（Android TraceExecutor.kt，以当前代码为准）
        
          
        下列为硬编码或可配置 delay 与 OCR 耗时叠加后的行为说明；OCR/截屏耗时随设备性能变化，文档不量化。
        
          
        For You 预滑（runForYouWarmupIfNeeded）：仅当 for_you_swipe_total_sec × 1000 ≥ 500 时执行。总时长内循环：每段随机观看 for_you_watch_min_sec～for_you_watch_max_sec（换算为毫秒且各自下限钳制为 500ms），每段不超过剩余总时长；若命中 for_you_like_prob，点赞双击发生在该观看段内的随机时刻（段足够长时 preDelay ∈ [40, watchMs−280) 毫秒；较短段另有分支）；段末执行上滑 swipe 后 delay(450)。
        
          
        从 Users 列表进入「当前任务用户名」对应主页（根用户，三种模式共用一段）：列表行点击后 delay(400)（失败会再点一次）；随后 delay(Random.nextLong(1200, 1800))；再执行一次 checkNoVideosAndGoBack（无作品/私密则 back 并结束本任务）。此处没有调用 checkNoVideosAndGoBackWithRetry。
        
          
          
            
        • growth：通过后立即进入 clickFollowersAndVerify，不在主页额外插入随机停留。该函数每次点击 Followers 后：第 1 次 OCR 轮询前 delay(2500)，第 2～4 次轮询间隔 Random.nextLong(500, 850)；最多 4 次轮询、最多 3 轮点击尝试。通过后进入粉丝列表，再 delay(Random.nextLong(1000, 2000)) 后执行 processFollowersList。
          • 
            
        • live / direct：通过后进入 runLiveVisitModeForCurrentProfile，很快对首条作品执行 tap（坐标见 4.4「首条作品」行）。live：点击后 delay(1500) 做首次帧差/OCR 判定，再 delay(secondCheckDelayMs)（默认 1100）二次判定。direct：点击后 delay(direct_post_action_delay_ms)（配置 300～8000ms），再 delay(900) 做第二次帧差判定。上述较长 delay 发生在已点击作品之后，用于判定/进入作品态；主页上除前述 1.2～1.8s 与无作品/私密 OCR 外无额外「资料页随机停留」。
          • 
          
        
          
        粉丝列表 processFollowersList（growth）：每条 OCR 行点击后 delay(Random.nextLong(1200, 1600)) 再分支。若命中 skip_post_click_prob：先 checkNoVideosAndGoBackWithRetry（内部最多两次检测，中间 delay(420)）；成功回列表后 delay(Random.nextLong(500, 800))；否则 clickProfileBack + delay(Random.nextLong(600, 900)) + delay(Random.nextLong(500, 800))，不执行点作品。未命中概率时：若 checkNoVideosAndGoBackWithRetry 为真则同样跳过。否则进入 enterPostAndRunInteractionsWithSecondCheck（先截屏再随机点左/中/右列作品，无额外「仅在主页」的随机等待）。单条处理结束后 delay(Random.nextLong(450, 750))。每轮列表向下滑动后 delay(Random.nextLong(900, 1200))。
        
          
        配置说明：video_stay_min / video_stay_max 作用于已进入作品页之后的互动前等待，不是资料主页停留。visit_delay_min / visit_delay_max 虽在服务端与 App 配置模型中存在，当前 Android 客户端执行路径未读取该字段。
